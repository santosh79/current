Yes. I’d turn this into a short progressive ladder, where each test unlocks the next one.

North star

A workflow with multiple intents should behave like a real execution pipeline:
	•	each intent is handled deliberately
	•	outputs accumulate
	•	the final WorkflowResult is a true bundle over produced artifacts
	•	failures have clear semantics

Proposed progression: 5 tests

1. workflow_result contains the exact produced artifact ids

This is the smallest next test and the best immediate lock.

Goal:
	•	approve a normal proposal
	•	collect every artifact_produced message
	•	receive workflow_result_assembled
	•	assert workflow_result.artifacts == Enum.map(produced_artifacts, & &1.id)

Why first:
	•	it strengthens the current model without forcing a redesign yet
	•	it tells you whether result assembly is actually faithful

⸻

2. proposal with multiple intents produces multiple artifacts

Introduce a MultiIntentProposalBuilder in test/support.

Goal:
	•	proposal has 2 intents
	•	after approval, you receive 2 artifact_produced messages
	•	workflow_result.artifacts has length 2
	•	workflow completes

Why second:
	•	this is the first true push beyond the one-intent assumption
	•	it forces you to decide whether artifact production is per-intent or per-workflow

⸻

3. multiple-intent workflow emits one effect event per intent or one per execution phase

This test is partly architectural: you choose the semantics and then lock them down.

Two valid options:

Option A:
	•	one :effect_applied per intent

Option B:
	•	one :effect_applied for the whole apply phase

Pick one and encode it.

Why third:
	•	you need to settle the event model before the system gets more complex

⸻

4. multiple-intent workflow fails when one intent fails

Use a builder that emits:
	•	one valid intent
	•	one failing intent, like :drop_database

Goal:
	•	define whether partial success is allowed
	•	likely expected behavior:
	•	:effect_failed
	•	:workflow_failed
	•	no final result
	•	maybe no artifacts persisted after failure, depending on policy

Why fourth:
	•	this forces the first real policy decision for multi-intent execution

⸻

5. workflow_failed event carries the correct terminal snapshot

You already test ordering. This would lock the payload.

Goal:
	•	assert failed event snapshot has:
	•	status == :failed
	•	error != nil
	•	result == nil
	•	approved proposal still attached

Why fifth:
	•	once multi-intent failure exists, you want the terminal record to be trustworthy

⸻
